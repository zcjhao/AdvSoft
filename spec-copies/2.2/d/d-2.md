# D.2: a killed HTTP node

Spec 2 of 3 for Component D (cluster robustness). Sections: 3 (rule numbers match the check
output). Check: `bash /spec/d/checks/check_d_2.sh`.

Do not start this spec until `check_d_1.sh` prints `RESULT: ... 0 failed`.

## Uses

Call these functions from D.1. Do not write a second version of any of them.

| Function | Used here for |
|---|---|
| `/app/start.sh` restart loops | Bringing the killed node back |
| `append_event(...)`, `event_pump()` | Delivery and replay on the surviving nodes |

## Adds

| Function | What it does |
|---|---|
| `resume(socket, channel_id, since_event_id)` | Sends every stored event after `since_event_id` in order, then `resumed` with the head (if not already built) |
| `on_node_start(node_id)` | Clears the presence rows of this node left over from before a crash |

No node may depend on another node being alive: there is no leader, no node-local state,
and no node forwards requests to another. A restarted node reads everything it needs from
the shared store.

## 3. A killed HTTP node

The check kills only the process that owns port `8001` (found with `ss -ltnp`), with
`SIGKILL`. Test it yourself the same way; never kill by name.

3.1 **Others keep answering.** Within 1 second after the kill, `8000` and `8002` answer
    `GET /api/health` with `200` and their own `node_id`.

3.2 **Reads and writes.** While `8001` is down, login, posting a message and listing
    messages work on `8000` and `8002`.

3.3 **Live delivery.** While `8001` is down, a socket subscribed on `8002` receives within
    2 seconds a message posted on `8000`, as `message.created` with the next `event_id`.

3.4 **Replay after reconnect.** A client whose socket on `8001` was cut by the kill
    connects to `8002`, sends `{"type": "resume", "channel_id": X, "since_event_id": N}`
    with the last `event_id` it saw, and gets every later event in order, then
    `{"type": "resumed", "channel_id": X, "head_event_id": H}`.

3.5 **The node comes back.** Without any action from anyone, `8001` answers
    `GET /api/health` with `200` and `node_id: 1` within 15 seconds of the kill (the
    `start.sh` loop restarts it in about a second).

3.6 **Back in the cluster.** After it is back, a message posted on `8001` reaches a socket
    subscribed on `8000` within 2 seconds, and a socket subscribed on `8001` receives a
    message posted on `8002`, all with consecutive `event_id`s.

Every request must answer within 5 seconds.
