## 0. Conventions (apply to every route in every spec of this component)

- Base URL `http://127.0.0.1:8000` (also `:8001`, `:8002`). All routes are under `/api/...`
  and return JSON with a single top-level resource key (`user`, `workspace`, `channel`,
  `message`, `messages`, `file`, `group`, `groups`, `reactions`, `members`, ...).
- `Authorization: Bearer <token>` on every route except register, login and health. Missing
  or invalid token → `401`, before anything else is checked.
- Status codes: `200` read/update, `201` create, `400` validation, `401` no/bad auth, `403`
  authenticated but not allowed, `404` unknown id, `409` conflict (duplicate, or editing a
  deleted message), `413` upload over the limit, `423` write to an archived channel. When
  several apply, answer in this order: `401` → `404` → `403` → `400` → `423` → `409`.
- Timestamps are ISO 8601 UTC strings ending in `Z`, for example `2026-05-16T08:07:34.123Z`.
- Ids are integers or strings, but always the same value on every node.
- **One shared store.** Anything created on one node must work on the other two at once.
  Keep all state (users, tokens, messages, files, events, presence) in one store that the
  node processes share, for example one SQLite file under `/app/data` (uploaded file bytes
  under `/app/data/files/`), never in per-process memory.

### Objects

- `UserObj`: `{id, username, display_name, timezone, avatar_url, status_text, status_emoji}`.
  `display_name` defaults to the username (or the `display_name` sent at register),
  `timezone` to `"UTC"`, the other three to `""`.
- `ChannelObj`: `{id, workspace_id, name, is_private, is_dm, topic, is_archived}`.
- `MessageObj`: `{id, channel_id, author_id, author, body, parent_id, reply_count,
  created_at, edited_at, files, reactions, mentions}`. `author` is the author's `UserObj`,
  `parent_id` is `null` for a top-level message, `reply_count` counts live replies,
  `edited_at` is `null` until the first edit, `files` is a list of `FileObj` (`[]` if none),
  `reactions` is `[{emoji, count, user_ids}]` (`[]` if none), `mentions` is a list of user
  ids (`[]` if none).
- **Events.** Every durable change to a channel appends one event to that channel's
  sequence: `{"type": <kind>, "event_id": <int>, "channel_id": <id>, ...extra}`. `event_id`
  starts at 1 per channel and goes up by exactly 1 per event (no gaps, no duplicates, the
  same ids on every node and on the IRC gateway). Allocate it inside the same database
  transaction that writes the change (`BEGIN IMMEDIATE`, then `MAX(event_id)+1`).

  | Change | `type` | Extra fields |
  |---|---|---|
  | new top-level message | `message.created` | `message` |
  | new reply | `message.reply` | `message` |
  | edit | `message.updated` | `message` |
  | delete | `message.deleted` | `message_id` |
  | reaction added / removed | `reaction.added` / `reaction.removed` | `message_id`, `emoji`, `user_id` |
  | user joins / leaves the channel | `member.joined` / `member.left` | `user_id` |
  | topic change | `channel.updated` | `channel` |
  | archive / unarchive | `channel.archived` / `channel.unarchived` | `channel` |

  A call that changes nothing (a repeated reaction, a second delete) adds no event.

## 1. The base this component needs

If `/spec` also holds the Component A and B specs (`roles/`, `channels/`), these routes are
already built by them: reuse them, do not write second versions. Otherwise build only the
minimal versions below (no roles, invitations, search, pins or read state), and nothing
else from Components A and B.

| Route | Minimal behaviour |
|---|---|
| `GET /api/health` | `200 {"status": "ok", "node_id": N}`, N = 0, 1, 2 for ports 8000, 8001, 8002 |
| `POST /api/auth/register` | `{username, password, display_name?}` → `201 {user, token}`; username letters/digits/underscore; password 8+ chars (else `400`); duplicate → `409`; token 16+ chars |
| `POST /api/auth/login` | `{username, password}` → `200 {user, token}`; wrong password or unknown user → `401` |
| `GET /api/auth/me` | `200 {user}` |
| `POST /api/workspaces` | `{slug, name}` → `201 {workspace: {id, slug, name, owner_id, join_mode: "open"}, general_channel}`; creates `#general`, the creator is its owner and a member of `#general` |
| `GET /api/workspaces` | `200 {workspaces}` the caller belongs to |
| `GET /api/workspaces/{slug}` | `200 {workspace, channels, read_state}` (channels the caller can see; `read_state` may be `[]`) |
| `POST /api/workspaces/{slug}/channels` | `{name, is_private?, topic?}` → `201 {channel}`; creator becomes a member; duplicate name → `409` |
| `POST /api/channels/{id}/join` | `200 {channel}`; a non-member of the workspace is added to it as a member |
| `GET /api/channels/{id}/members` | `200 {members: [UserObj]}` |
| `POST /api/channels/{id}/messages` | `{body, parent_id?, file_ids?}` → `201 {message}`; blank body → `400`; non-member of a private channel → `403`; archived channel → `423` |
| `GET /api/channels/{id}/messages` | `200 {messages, next_cursor}` top-level messages, newest first (`?limit=` default 50) |
| `GET /api/messages/{id}/replies` | `200 {replies, next_cursor}` oldest first |
| `ws://…/api/ws?token=<token>` | refuse a bad token before the upgrade (no `101`); `{"type":"subscribe","channel_id":X}` → `{"type":"subscribed","channel_id":X,"head_event_id":H}`, then every later event of X; `{"type":"resume","channel_id":X,"since_event_id":N}` → every event after N in order, then `{"type":"resumed","channel_id":X,"head_event_id":H}` |

Rules 1.1 to 1.6 are in the check of this file:

1.1 **Health.** All three nodes answer `GET /api/health` with `200` and their own `node_id`.

1.2 **WebSocket token.** An upgrade with a made-up token is refused (not `101`); a real token
    gets `101`.

1.3 **Auth.** Register (`201`, token of 16+ chars), duplicate register (`409`), login on
    another node (`200`), and `GET /api/auth/me` with the token on all three nodes (`200`,
    same user id); without a token → `401`.

1.4 **Workspace and channel.** Create a workspace (`201`, `owner_id` is the caller,
    `general_channel.name` is `"general"`), another user joins `#general` on another node
    (`200`), create a channel on a third node (`201`).

1.5 **Messages.** Post (`201`, full `MessageObj` as above), reply with `parent_id` (`201`),
    blank body (`400`); the listing is newest first with `next_cursor`, holds no replies,
    and the parent shows `reply_count: 1`; `GET /api/messages/{id}/replies` lists the reply.

1.6 **Live events.** A socket on `8002` subscribes to `#general`; a message posted on `8000`
    arrives within 2 seconds as `message.created` with `event_id` = head + 1 and the
    message. Each node delivers new events to its own sockets by polling the shared events
    table every 50 ms (do not rely on Redis for delivery, see Component D).

## 2. The supervisor and a killed Redis

`/app/start.sh` stays in the foreground for the whole run and keeps five things alive, each
in its own restart loop, then `wait`s:

```bash
#!/bin/bash
cd /app
mkdir -p /app/data
( while true; do redis-server --port 6379 --bind 127.0.0.1 --save '' --appendonly no; sleep 0.5; done ) &
for i in 0 1 2; do
  ( while true; do python3 /app/server.py node $i 800$i; sleep 0.5; done ) &
done
# the IRC gateway (Component E) gets its own loop the same way, if it is built:
# ( while true; do python3 /app/server.py irc 6667; sleep 0.5; done ) &
wait
```

Durable events never depend on Redis: the event id comes from the database transaction, and
each node's `event_pump` reads new events from the shared table. Redis is only a
notification channel on top (a node may `PUBLISH` after each commit and wake its pump
early). So when Redis dies, nothing changes for clients. Never call Redis inside the
request path without a short timeout and a `try/except` around it.

2.1 **Redis is up.** A Redis server answers `PING` with `+PONG` on `127.0.0.1:6379`.

2.2 **Writes survive a dead Redis.** The check kills the process that owns port `6379`
    (`SIGKILL`). Right away, a message posted on each of `8000`, `8001` and `8002` returns
    `201` within 5 seconds.

2.3 **Fan-out survives a dead Redis.** The three messages of 2.2 reach a subscriber on
    another node within 5 seconds, as `message.created` events with consecutive
    `event_id`s (no gap, no duplicate).

2.4 **Redis comes back.** `/app/start.sh` restarts Redis: it answers `PING` again within
    10 seconds of the kill, with no action from anyone.

2.5 **Normal after the restart.** After Redis is back, a message posted on `8001` reaches
    subscribers on `8000` and `8002` within 2 seconds with the next `event_id`.

Every request must answer within 5 seconds.
